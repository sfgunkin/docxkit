# docxkit — architecture review, 2026-10-12

The fifth review. The four before it ([`08-15`](REVIEW_2026-08-15.md),
[`09-01`](REVIEW_2026-09-01.md), [`09-03`](REVIEW_2026-09-03.md),
[`09-28`](REVIEW_2026-09-28.md)) asked about the import graph, the
substrate, result contracts, CI cost, versioning and the quality
apparatus, and every row they raised has been answered. This one doesn't
re-measure those. It asks a question none of them did: **how does the
package know that its model of Word is right?** Every gate in the
protocol stands on that model, `revisions.accept` and `revisions.reject`.

The question came out of the fix in `64b1b0a`. For two months the reject
simulation left a deleted field's `w:delInstrText` in place. Gate 5
called every such link LOST, and that wrong answer was written up as a
fact about Word. It wasn't one.

**Measured on** `120f924`, Python 3.14.7, this machine. **Tools:** a
census of revision markup in every kept redline of the registered papers
(115 files), and in 106 `*redline*.docx` across `Papers/`. Gate 5
was run offline against real baselines, before and after `64b1b0a`. An
AST pass split `src/` into code, docstrings and comments, and the
registered papers' `log.md` files were searched. The scripts were session
scratch and are not committed. The defect marked **→ BACKLOG** was
reproduced before it was filed.

**Scale:** `src/` 47,221 physical lines (+2 % since 09-28), `tests/`
120,362, `tools/` 10,785; 9,424 tests collected. 41 commits since
`7df04c3`, 27 of them touching `src/`. That ratio is healthier than the
31 % the last review measured.

**Verdict.** The engineering is sound and the last review's agenda is
done. The weak point now is **epistemic, not structural**. The package
measures everything about its own code, but it checks its model of Word
against Word in exactly one place. That one check covers only the
accept side and only main-story text. The reject side, which the
protocol uses to promise the author a real veto, has never been checked
against Word by any code. So a model defect can't be told apart from a
Word behaviour. When one turned up, the package's habit of writing
measurements into docstrings spread it: into seven places in the repo,
a memory file, a paper's log, and one round's protocol design.

## 1. The model of Word has one oracle, and it is half an oracle

**What the protocol promises.** `validate`'s docstring says gate 5 is
what makes the author's veto real: rejecting everything must reproduce
the baseline. Gate 5 compares paragraphs, glyphs, footnotes, LINKS and
structure, and it computes all of them from `rejected_view`, which is
`revisions.reject`. That is this package's simulation, not Word's.

**What checks the simulation.** Gate 6 checks it once:
`_validate.py:472` runs Word's `AcceptAllRevisions` in the session gate 3
already opened, and `:550-553` compares the main-story glyph stream
against the XML accept. Three limits follow:

- **Accept only.** Nothing in `src/`, `tests/` or `tools/` calls
  `RejectAllRevisions`. Gate 5's model has never been compared with Word
  in code. The reviewer who found the `delInstrText` defect on 10-10 did
  it by hand.
- **Text only.** The comparison is `_norm(_glyph(...))`. Links, notes,
  bookmarks and structure (the arms gate 5 adds) aren't compared on
  either side. A link-shaped model defect passes gate 6 by construction.
- **Rarely run.** The `-m word` suite is 8 tests and is deselected by
  default; CI's Windows runner has no Word.

**What the gap cost.** Before `64b1b0a`, gate 5 on Aging_Well's
2026-10-10 batch against its real `prev.docx` reported `links: False`
with 11 links lost. After it, all five arms pass. The rejected view of
the 2026-09-02 redline (R79's date) held 211 links before the fix and
221 after, which matches the log's "cost TEN links on the reject side". Those
results became doctrine:

- `_losses._links`, `links_in_deletions`, the build warning, the `LINK
  LOST` console line and three test docstrings all said "Compare does
  not rebuild a link inside a rejected deletion".
- The convention to "mint links after the handback" and the "shorten the
  move" remedy came from the same results.
- So did R79's design. Its protocol froze a byte-identical release copy
  and defined rejection as restoring it, explicitly because the reject
  side was "links-unclean". That was an architectural workaround for a
  defect in this package.

**The census found another one.** Of the OOXML revision elements, 26 were
compared against what `revisions.py` names. `w:tblPrExChange` (a tracked
change to a row's `w:tblPrEx`) is in none of `_PROPERTY_CHANGES`,
`_REVISION_NAMES` or `_PROPERTY_MARKERS`. On a probe it counts as 0
revisions, accept keeps it, and reject doesn't restore the old
properties. It occurs in a real redline (`CC_age_gap`, 2026-10-03).
**→ BACKLOG S1.** `w:numberingChange` is in the same position, with no
occurrence yet.

**Recommendation.**

1. **A reject oracle in the ladder.** Gate 3 already opens Word. Open a
   temporary COPY of the batch (the author's window is never touched,
   which keeps the docstring's promise) and run `RejectAllRevisions`.
   Then compare *the same five arms gate 5 computes*, not glyphs: link
   multiset, note texts, paragraph texts, structure counts. Extend gate
   6 the same way on the accept side. A build already spends 40–141 s
   in Word (09-28 §7), so a second open of seconds doesn't change its
   shape. A
   disagreement there names a model defect directly. Today it shows up
   as an author's mystery.
2. **A conformance sweep, `tools/word_oracle.py`.** Run model against Word
   on both views over the kept redlines (115 on this machine, and
   growing by one per round). Run it when `revisions.py` changes and
   nightly where Word is installed. Each disagreement becomes a backlog
   entry. This is the `golden`/`sweep` pattern with Word as the oracle
   instead of the last recorded answer.
3. **One table of revision elements.** `_PROPERTY_CHANGES`,
   `_REVISION_NAMES` and `_PROPERTY_MARKERS` are three hand-kept lists
   of overlapping facts, and the omission was in all three. Derive them
   from one table that gives each element's kind (content wrapper,
   property snapshot, range marker, cell flag) and its schema position.

## 2. The fixture vocabulary is imagined, not harvested

**Measured.** I collected every element name inside a `w:del`, `w:ins`,
`w:moveFrom` or `w:moveTo` across the 115 kept redlines, then checked
whether any test puts that name within six lines of a revision wrapper.
`w:delInstrText` occurs 194 times in 19 redlines. Before today it was in
no fixture inside a revision. The only fixtures for "a link inside a
deletion" used the ELEMENT form (`w:hyperlink` in `w:del`). In Aging_Well's
kept redlines Compare wrote that form in 2 and the field form in 16, and
the model always handled the element form. The test suite modelled the shape its authors pictured, and Word
writes a different one. Others in the same position: `w:rFonts` in 44
redlines and `w:vertAlign` (note markers) in 3 are fixtured only outside
revisions; `w:highlight` in 4 redlines is in no test at all.

**Recommendation.** Make the census a gate (`tools/shapes.py`, skipping
without `DOCXKIT_CORPUS` like its siblings). The set of element names
Word writes inside revisions, minus the set fixtured inside revisions,
is a list of untested shapes. Each one is either fixtured or declared
irrelevant in a table, the same discipline the regex registry applies
to patterns. Better still, cut fixtures from real redlines: a shape
harvested from Word's output can't be one Word doesn't write.

## 3. The goldens freeze answers; they don't check them

`tools/golden.py` fingerprints four frozen manuscripts and was unchanged
across `64b1b0a`. That is correct for what it measures, and it is why it
can't help here. The documents are finished, nearly revision-free
papers. The reject view is fingerprinted as text, and the field result's
text never changed. Links are counted on the document as-is, not on
either view. A golden detects that an answer MOVED. It can't say the
recorded answer was right: had a redline been frozen in September, its
digest would have recorded the 211-link view as truth.

**Recommendation.** Add two or three kept REDLINES to the goldens, and
fingerprint each view's link multiset and note texts, not just its
text. Where Word is available, record the answer `word_oracle`
confirmed, so a golden is checked once against Word and frozen
afterwards.

## 4. Testimony without its instrument

**Measured.** Of `src`'s 41,046 non-blank lines, 58 % are code, 28 %
docstrings and 13 % comment-only. It holds 450 `YYYY-MM-DD` references
and 354 citations of papers by name. The highest prose-to-code ratios are
`revision/_losses.py` (1.38), `_xml.py` (1.28) and `_cite_grammar.py`
(1.18). `_losses.py` is where the false claim lived.

The prose is mostly excellent, and the house rule to argue a decision
once, in the docstring, is right. The failure was narrower. **A
measurement was recorded without its instrument.** "Measured on
Aging_Well R24: `links: False`" was true. What it left out was *through
which reject*: docxkit's simulation, not Word's. The next sentence
promoted it to a fact about Compare, and seven restatements later
nobody could tell the observation from the inference.

**Recommendation.** A claim about what WORD does gets one of two labels
where it's written down: a `word` test that witnesses it (cited by
name), or the words "observed through docxkit's model". That's the
claims-ledger idea applied to behaviour, not to mutants. Start with the
claims that gates or remedies depend on: Compare and anchors, Word's
save dropping parts, accept stripping run properties. Each one is a
candidate `-m word` test, and the 8 that exist show the harness works.

## 5. Identity across versions is a derived key

The `baseline` S4 attempt (`344f49c`, reverted in `4deb0f9`) failed for
one reason that appears in five of its eight review findings. It
matched a loss to the batch's deletion by a DERIVED key. A repeated
citation shares one `(anchor, label)` key. `_lost_notes` names a note
best-effort from sorted texts. A stamp isn't invalidated when a promote
is undone. The same keying runs through `_links` (a multiset of pairs)
and `_lost_or_retargeted`. A multiset is the right instrument for "did
reject-all return the baseline". It's the wrong one for "is this loss
the batch's own deletion", which is a question about the identity of
one occurrence.

**Recommendation.** Before the S4 is redesigned, decide how an
occurrence is identified across baseline → redline → hand-back. The
redline already carries the answer: an item's position in it, mapped
through its own revision marks, identifies the occurrence. The redesign
note in BACKLOG already asks for this ("match the actual tracked
deletion … not a derived key"). This section is the argument for doing
that as a primitive in `_losses`, available to every loss check, not
inside `_losses` for one command.

## 6. Smaller

- **A library call with a user-global side effect.** `revision.init`
  registers into `%LOCALAPPDATA%\docxkit\papers.txt`, the only such
  write in `src/` (`_registry.py:37`). 86 of 98 rows were scratch
  projects on 10-10. The open S2 proposes refusing Temp paths. The
  architectural fix is that registering is the CLI's decision (`docxkit
  revision init` registers; `revision.init()` doesn't unless asked),
  and a library caller never mutates a file it didn't name.
- **`links_in_deletions`** is now a warning about the wrong form, open
  as S2. It should be decided once §1's oracle can say what Word
  actually loses.
